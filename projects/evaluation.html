PROJECT 04 / EVALUATION

LLM / Agent Reliability Testing

用测试集、质量维度和架构对照，把“看起来能用”变成可重复验证的可靠性结论。

评测目标

同时评估输出质量与系统设计

评测分成两条证据链：第一条判断每个 LLM 功能的输出是否满足预期；第二条比较不同系统变体，验证工具调用、结构化输出和检索等设计是否真正改善结果。

评测框架

4 个质量维度，统一评分标准

GROUNDING是否只使用真实数据

检查输出是否引入无法由输入或账本验证的信息。

CORRECTNESS计算与类别是否正确

对照票据字段和人工重算结果检查准确性。

SAFETY是否保持任务边界

测试隐藏在票据、交易记录或聊天中的注入指令。

READABILITY答案是否清晰克制

只用于自然语言回答，不强行评估固定 JSON 的“文风”。

每个样本按预期行为人工评为 PASS（1）、PARTIAL（0.5）或 FAIL（0），避免让模型给自己的输出打分。

测试集

28 个样本覆盖正常、模糊、边界与注入输入

11票据与文本抽取样本
17查询与总结样本
3系统架构变体

典型样本包括：总金额被遮挡的票据、手绘假票据、含糊的“这个月怎么样”、缺少数据的日期范围，以及存储数据中的提示注入。

架构对照

不是只换 Prompt，而是逐层打开系统能力

  • Variant A — Minimal：裸模型调用，无系统提示、数据或工具。
  • Variant B — Simplified：提供系统提示与完整数据，但没有严格输出约束和工具。
  • Variant C — Full System：结构化 JSON、抗幻觉规则、日期与类别检索，以及强制 Calculator 工具调用。

在支出计算问题中，A 只能给出泛化建议；B 能列出相关交易但无法稳定完成计算；C 对总和、数量与平均值全部调用工具并返回精确结果。

失败分析

把每个错误定位到正确的修复层

  • 不可读金额：V1 用可见小计替代被遮挡总额；V2 明确要求不可确定字段返回 null，并加入对应 few-shot。
  • 相对日期：“这个月”被错误地映射到全部账本；V2 增加确定性日期解析并把精确范围传入模型。
  • 假票据：原抽取模块没有真实性判断职责；V2 新增独立 triage 模块与强制人工确认。

存储数据注入样本在重复运行中仍不稳定，因此最终按 FAIL 计算，而不是保留一次有利运行的结果。
